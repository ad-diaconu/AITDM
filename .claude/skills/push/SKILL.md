# /push: commit and push by CONTRIBUTING.md

The user invoked this skill, so they are asking you to commit **and** push without confirming each step.
Stop and ask only in the cases listed under "When to stop and ask".

`CONTRIBUTING.md` at the repo root is the source of truth. **Read it in full first, every time.** If it disagrees
with anything below, CONTRIBUTING.md wins. Do not rely on a remembered copy of it.

Repo: `ad-diaconu/AITDM`. Planner (optional): GitHub Project "AITDM project planning" (#2, owner `ad-diaconu`).

Arguments: `$ARGUMENTS`
- Free text is a hint about what the work is (use it for the type, scope, summary and branch name).
- `#<n>` names the issue this work belongs to.
- If it contains `pr`, also open a pull request at the end (step 7).

## 1. Look at the state

```
git status --porcelain
git branch --show-current
git diff --stat HEAD
git diff HEAD
git log --oneline -10
git config --get aitdm.owner
```

Look at what untracked files are. Skim large results files instead of dumping them. If nothing has changed and
nothing is unpushed, say so and stop.

## 2. Check for things that must not be committed

Do not stage, and tell the user about:
- data: anything under `data/` (git-ignored, regenerated by `data_splitting/`), raw WISDM archives (`*.tar.gz`)
- model weights (`*.pt`, `*.pth`, `*.ckpt`), `logs/`, Slurm logs (`*.out`, `*.err`), `__pycache__/`, `.venv/`
- ad-hoc runs (`outputs/sim-*`, `outputs/deploy-*`) and explainability scratch output nobody asked to keep
- personal Claude files: `.claude/skills/*` other than `push`, `.claude/reviews/`, `.claude/settings.local.json`
- secrets (`.env`, tokens, keys) and any other single file over ~50 MB

If a `results.json` looks hand-edited (a few numbers change but no run was done), stop and ask.

**Provenance check.** Results fetched from the cluster carry a `COMMIT` file per run. If it ends in `-dirty`, or the
runs of one experiment have different commits that touch the compared code, stop and ask: dirty results must not go
into a `results(...)` commit.

## 3. Find the issue (optional)

The repo may have no issues yet; work does not need one. Use one if it exists, in this order:
1. `#<n>` in the arguments.
2. An open issue whose title clearly matches the work (`gh issue list -R ad-diaconu/AITDM --state open`).

If none fits, carry on without one (commits and PRs alike); do not create issues unless asked.

## 4. Get on the right branch

Never commit on `main`.

- **Owner handle**: `git config --get aitdm.owner`. If empty, infer it from earlier branches (`git branch -a`,
  `git log --merges`; e.g. `ad-diaconu/...`). If still unclear, ask once and save it with
  `git config aitdm.owner <handle>`.
- **If on `main`**: create `<owner>/<type>-<short-description>` (CONTRIBUTING.md §3): the type of the main goal,
  kebab-case, 2 to 5 words, with split / K / model / strategy when they matter (`exp-fedprox-s2-k5`). Then
  `git switch -c <branch>`; uncommitted changes move with you.
- **If on a feature branch**: stay on it. If the changes clearly belong elsewhere, mention it, but do not move them.

## 5. Plan and make the commits

Split the changes into single-purpose commits (CONTRIBUTING.md §2): types `exp`, `data`, `model`, `train`, `eval`,
`results`, `viz`, `infra`, `docs`, `fix`, `refactor`, `perf`, `test`, `chore`; scopes as in §2.3 (`baseline`, `fl`,
`wisdm`, `partitions`, `fcn`, `lstm`, `fedavg`, `fedbn`, other strategy names, `dp`, `attack`, `xai`, `fep`,
`scripts`, `ci`, `report`; add a new short one if needed).

- **Summary**: imperative, lower case, no trailing period, at most ~72 characters. Body only when the *why* is not
  obvious.
- **Code first, results second.** If both code (`*.py`, `*.sbatch`, `experiments/runs/*.txt`, templates) and outputs
  (`outputs/**`: `results.json`, `COMMIT`, `summary*.json`, `report.html`) changed,
  commit the code first, then a `results(<scope>)` commit with `Code: <short hash>` (for cluster runs: the hash in
  their `COMMIT`, which must be an existing commit).
- **Results trailers.** For a `results` commit read the changed `summary*.json` (or the new `results.json` files) and
  add `Metrics:` with headline test macro-F1 as mean ± std; numbers you actually read from the files, never
  estimated. Add `Config:` with the run list (`experiments/runs/<list>.txt`) or command and, for cluster runs, the
  job ID(s). Add `Seeds:` / `Folds:` only when coverage is not the default 5 × 3.
- **`Refs:`** the issue (`Refs: #3`) and `RQ<N>` when clear (`docs/experiment_setup_*.md` list the RQs). Do not put
  `Fixes` in commits; the PR closes the issue.
- **Results-breaking (`!` + `BREAKING-RESULTS:` trailer).** Consider it whenever the diff changes preprocessing,
  windowing, normalisation, labels, folds, test users, client partitions, metric definitions or default
  hyperparameters, e.g. `data_splitting/prepare_wisdm.py`, `split_data.py` / `partitioning.py`, the models / metrics
  in `fl_app/aitdm_fl/task.py`, `DEFAULTS` / `fl_app/pyproject.toml`, best-round / best-epoch selection. See
  "When to stop and ask".

Stage exactly each commit's files (`git add <paths>`, never `git add -A` or `git add .`), then commit with a heredoc:

```
git commit -F - <<'EOF'
<type>(<scope>): <summary>

<body>

<trailers>
EOF
```

Do not use `--no-verify` or `--amend`. If a hook fails, fix the cause and make a new commit. Run `git status` at
the end to confirm nothing intended is left over.

## 6. Push

```
git push -u origin <branch>
```

Never push to `main` and never force-push. If rejected because the remote branch moved, run
`git pull --rebase origin <branch>` once; on conflicts, stop and tell the user. If remote `main` has moved ahead,
mention it (CONTRIBUTING.md §3.3 asks for a rebase or merge before the PR), but do not rebase unless asked.

## 7. Pull request (only if `pr` was passed)

If a PR for the branch already exists (`gh pr view --json url`), do not open another; report its link.

Otherwise fill in `.github/pull_request_template.md` (read it; keep its headings) and open the PR:

```
gh pr create --base main --head <branch> --title "<type>(<scope>): <summary>" --body-file <filled template>
```

- **`Fixes #<n>`** with the issue from step 3, so merging closes it; delete the line if there is none.
- **Research question**, **Results** (metrics read from the files, paired difference / wins / Holm p from
  `summary_fl.json`, or `n/a`) and **Reproduce** (run list or command, job IDs, `COMMIT`).
- Tick the checklist items that are true; for results-breaking PRs, list what must be re-run.
- Title in commit-message format. Write the body to the scratchpad, not the repo.

If `gh` is missing or not logged in, print the title and body so the user can paste them.

## When to stop and ask

One short question, then carry on, only when:
- a change might be results-breaking and it is unclear whether it changes outputs (`!` or not?);
- the provenance check from step 2 triggers (dirty or mixed commits in results);
- the owner handle cannot be found;
- something from step 2 was found and it is unclear whether the user meant to commit it;
- a push or rebase fails in a way you cannot safely resolve.

Everything else, decide yourself using CONTRIBUTING.md.

## Report

End with: branch name, linked issue (if any), each commit as `<hash> <subject>`, the push result (or PR link), and
anything skipped or flagged.
